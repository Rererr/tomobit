## Context

ADR-0028 Decision 5 は、分割の子について「主観Feedbackは聞かない、客観信号だけで
経験になる」と決めた。ADR-0051 / ADR-0052 の実装後に台帳を読み直したところ、
**その客観信号が一度も鳴っていなかった**:

```text
分割の子   13セッション / provider.error 0件 / test.result 0件 / 主観は設計上聞かない
親・通常   36セッション / provider.error 3件
```

`OutcomeWeight` は子について必ず `ok=false` を返す。**台帳の27%が、Connectionを
1ミリも動かしていない。** これを「子の無信号」として次の論点に開いてあった。

論点を詰める過程で、コードから3つの事実が出た。**設計より先に、事実の方が答えを
決めた。**

### 事実1: タスクの親子は、学習の層に存在しない

[ADR-0013](ADR-0013-prior-inheritance-mean-only.md) の親子は **Connection の scope の親子**
（粗い棚 → 細かい棚）であって、タスクの親子ではない。子セッションの経験は
`perceiveSession` が**子自身のイベントから意味を取り直して**作り、普通のタスクと
同じ棚に落ちる。**子専用の棚は無いし、親と子を結ぶ線も無い。**

問いは「子に Connection を持たせるか」ではなかった。
**子の実行を、普通のタスクと同じ棚に混ぜてよいか**だった。

### 事実2: 入口と出口で棚が違う（auto のとき）

`openSubtask` は `providerName == "auto"` のとき、**子ごとに** `autoDecide` を呼ぶ。
そのとき渡している `tp`（taskPerception）は**親の intent から作られたもの**である。

```text
決定  autoDecide が 親の意味 {go, auth} の棚を見て codex を選ぶ
記帳  perceiveSession が 子の意味 {go, redis} の棚へ結果を書く
```

**引いた腕と、更新する腕が違う。** Thompson サンプリングは「引いた腕の結果でその腕を
更新する」から収束する。この形では収束しない。

しかも子ごとの `autoDecide` は3本とも**同じトークン**で引いており、違いは乱数だけ。
「Redis は codex が得意そうだから codex」ではなく、**中身を見ずにK回くじを引いている**。
tomobit が子を「見て」選んでいる、という前提自体が実装に無かった。

### 事実3: 分割の子は、親の作業場所を継いでいなかった

親のターンは `WorkDir` / `AddDirs` を積む。分割の子の `executor.Request` には
**どちらも無い**。`cmd.Dir` が空なので、子は **tomobit 自身の cwd** で走る。

GUI は常に `--cd` を渡す。つまり実運用で:

```text
親  ~/repos/myapp        で働く（さらに隔離先の worktree へ）
子  tomobit-gui の cwd   で働く   ← 別のリポジトリ
```

**子は違うコードベースで作業していた。** 失敗もしない — Provider は立ち上がり、
そこにあるものを読み、それらしい答えを返す。ADR-0050 Decision 3 が
「サブタスクは親の隔離を継ぐ」と書いた前提も、ここで成立していなかった
（duel の子には `AddDirs` が渡っている。**分割の子だけが漏れていた**）。

### 所有者の判断（2026-07-27）

事実2 を「どちらに倒すか」が、そのまま論点の答えだと整理して問うた:

```text
子ごとに意味を取り直して決める   → 子は独立した発注。tomo が採用している。評価する
親の意味で統一する               → 子は親タスクの一部。tomo の相手は親1人。評価しない
```

所有者は**後者**を選んだ。その根拠として先に置かれていた比喩:

> 人事として Tomo を見た時、採用したメンバーがオフショアした先のチームの評価まで
> する必要はない

この比喩が引いているのは木の深さの線ではなく、**契約の深さ**の線である。そして
事実2 が示したのは、tomobit は `auto` でも子を**契約していない**ということ —
子を見て選んでいないので、そこに人事は発生していない。

## Decision 1: 決定は親で1回。子は親が選ばれた相手で走る

`openSubtask` から `autoDecide` を外す。分割の子は**親のアダプタをそのまま**受け取る。

```text
これまで  親: autoDecide → claude     子1: autoDecide → claude
                                      子2: autoDecide → codex     ← 乱数
                                      子3: autoDecide → claude
これから  親: autoDecide → claude     子1..3: claude              ← 決定は1回
```

- **`tomo.decided` は分割の子に載らなくなる。** 決定が1つしか無いのだから、
  記帳も1つ。ADR-0043 の auto は**親でだけ**効く
- **子が `human` に抽選されることも無くなる。** 分割はタスクの内訳であって、
  内訳の一部だけを人へ差し戻す経路ではない（人へ渡したいなら `--provider human`
  でタスクごと渡す道が既にある）
- `openSubtask` は「子セッションを開く」だけの関数になる。アダプタの解決という
  別種の仕事を持たなくなり、[ADR-0011](ADR-0011-meaning-by-model-judgment-by-math.md) の
  「判断の席」がタスクにつき1つに戻る

### 却下: 子ごとに perception を取り直して、子の意味で決める

事実2 のもう片方の倒し方。棚のズレは直るし、「Redis は codex」のような
本当の適材適所が可能になる。却下する理由は3つ:

1. **知覚コストがサブタスクの数だけ増える。** 分割の平均は3.25本なので、
   1タスクあたりの知覚が4倍を超える。ADR-0036 が「遅延して1回」に絞った理由が
   そのまま逆に効く
2. **子は親の文脈を持たない。** 子セッションのイベントは
   `task.started {intent: サブタスク文}` から始まる。「Redisセッション実装」
   だけを見て取った意味は、親の「認証まわりのリファクタ」を落としている。
   細かい棚に見えて、実際は**文脈を失った棚**になる
3. **これは tomobit がオーケストレーションを始めるということ。** VISION の
   「Tomo はオーケストレータではない」に正面から触れる。分割の中身をどう配るかは、
   分割を提案した Provider の采配であって、tomobit の仕事ではない

## Decision 2: 分割の子は経験にしない。経験の単位はタスク1つ

`PendingSessions`（Deferred Perception のキュー）から分割の子を除外する。
**子のイベントは1バイトも消さない** — One Ledger のとおり、変わるのは投影だけである。

```text
台帳    task.started / provider.* / task.finished …  子の分も全部残る
経験    親セッションから1件だけ                       ← 変わるのはここ
```

除外の形は「子を除く、ただし duel の子は除く」ではなく、
**「親を持つセッションは既定で経験にしない。duel の子だけが例外」**とする。
新しい親子関係が将来生まれたとき、既定が「内訳」側に倒れる方が本ADRの原則と
一致するからで、独立した発注として扱いたければ**明示的に opt-in する**ことになる。

### これで片側の非対称が消える

現状の子は**失敗だけ**が `y=0` で乗り、成功は `ok=false` で何も乗らない。
片側だけの証拠は、証拠が無いより悪い:

```text
Provider A  子を100本、エラー0回  → 1度も観測されない → Beta(1,1)  平均 0.50
Provider B  子を100本、エラー5回  → 5回 Observe(0)   → Beta(1,6)  平均 0.14
```

**成功率95%の B が、一度も測っていない A より下に並ぶ。** まだ発火実績は無い
（子13件でエラー0件）が、`auto` が既定になった以上これは時限式だった。
Decision 2 は副作用としてこれを外す — 評価しないなら罰も与えない。

### ADR-0028 Decision 5 の撤回

同 Decision の「子は客観信号だけで経験になる」は**撤回する**。同 Decision の
残り（主観Feedbackは区切りで1回だけ、統合を語った親に乗せる）は**不変**で、
むしろ本ADRの後は**それが分割の唯一の学習経路**になる。ADR-0051 が親に足した
采配の評価も、同じ場所に立っている。

### 却下: 経験行は作るが、学習だけ止める

行を残せば「何が起きたか」が experiences テーブルからも読める、という利点がある。
却下する理由は、**永遠に `ok=false` を返す行は経験ではない**から。
[ADR-0018](ADR-0018-experience-sovereignty.md) の経験主権は
「人が答えたものが経験になる」と置いており、誰も答えていない行を経験の棚に
置き続けるのは、その線を曖昧にする。加えて `capVocab` が経験から語彙を作るので、
サブタスク文由来の語が意味の語彙を薄める実害もある。

### 却下: 親の主観を子へ一様 1/K で配る

起草者が先に出した案。`Observe` を重み付きに一般化し、K人の子へ `y` を重み `1/K`
で配れば、ADR-0028 Decision 5 の却下理由（(a) 配分比という采配判断が生まれる、
(b) 信号が相関する）は形式的には両方溶ける。却下する理由は、**人は子を1つも
見ていない**から。見ていないものへ主観を写すのは、按分の形を変えても
経験主権に触れる。機構が先にあって理屈を後付けした案だった。

## Decision 3: 子は親の作業場所で働く

分割の子の `executor.Request` に `WorkDir` / `AddDirs` を渡す。事実3 の修正であり、
Decision 1・2 と同じ原則から出る — **子は親タスクの一部なのだから、同じ場所で働く**。

さらに、親が隔離を宣言していた場合（`task.workspace` の `isolated:true`）は、
**宣言された `path` を子の cwd にする**。これで ADR-0050 Decision 3 の
「隔離の単位はセッションの木」が、初めて実装として成立する。

`path` を使う前に**ディレクトリとして存在するかだけ**を見る。存在しなければ親の
`WorkDir` へ落とす。これは ADR-0050 Decision 2 の「検証はしない」に触れない —
そこが本当に worktree かは相変わらず確かめないし、確かめられない。見ているのは
**chdir できるか**だけで、`--cd` に対して既にやっている `checkWorkingPlace` と
同じ種類の確認である。宣言が壊れていたときに全ての子が起動エラーで死ぬ方が、
黙って元リポで働くより悪い。

## Consequences

- **分割の子から `tomo.decided` が消える。** 台帳の `tomo.decided` 件数は
  分割の多い期間で下がる。決定の回数が減ったのであって、決定が隠れたのではない
- **experiences に分割の子の行が新規に作られなくなる。** 既存の行はそのまま残る
  （One Ledger: 過去を書き換えない）。`extractor_ver` を上げて再知覚したときに、
  はじめて投影から落ちる
- **`OutcomeWeight` の `Failed` は duel の子のためだけに残る。** コメントが
  「subtask/duel child」と書いているので、subtask を外す
- **ADR-0026 は無傷。** duel は「2者を比べる」ために**わざと別々に指名している**
  ので、その子は本当に独立した発注である。本ADRの唯一の例外として明示する
- **ADR-0051 の采配評価が、分割の唯一の学習経路になる。** 分割の質が測れる場所は
  親の主観Feedback + `user.split_verdict` の2つだけになり、責任の所在が1つに揃う
- **索引 / SCHEMA**: 新しいイベント型は作らない。SCHEMA.md の
  `task.started.parent` と `tomo.decided` の説明に、分割の子の扱いを追記する

### 所有者が決めたこと / 起草者が決めたこと

Status を Accepted にしているのは、**方針そのもの**（「親の意味で統一する」）が
所有者の選択だからである。そこから派生した次の決めは起草者が置いた:

- Decision 2 の除外の形を「親を持つ子は既定で除外、duel だけ例外」にしたこと
  （「分割の子を除外」ではなく、既定を原則側へ倒した）
- Decision 3 で、隔離先を子の `WorkDir` にすること（`AddDirs` に足すだけでも
  動くが、それだと子が元リポで働き続ける）
- Decision 3 の存在チェックとフォールバック

いずれも手戻りの効く範囲なので実装した。**違うと思うものがあれば戻す。**

## 実装フェーズ

1. **Decision 3 だけ先に**（事実3 は論点と無関係な実害）: 分割の子へ
   `WorkDir` / `AddDirs` を渡し、隔離先があればそこを cwd にする
2. **Decision 1**: `openSubtask` から `autoDecide` を外し、親のアダプタを渡す
3. **Decision 2**: `PendingSessions` の除外と、`OutcomeWeight` のコメント修正
4. 既存ADR（0028 / 0043 / 0047 / 0050 / 0051 / 0026）と SCHEMA.md への追記
