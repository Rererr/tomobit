## Context

2026-07-30、所有者が chat でこう言った——「**codex でも並列で実行して欲しい**」。

起きたことは次のとおりである。tomobit はその文をプロンプトの一部として claude-code へ
渡した。claude-code は要求を理解し、**Bash で codex CLI を起動して**それを満たした。
作業は成立した。しかし台帳には `claude-code` の成果としてだけ残り、codex という語は
どこにも無い（道具名だけを記帳する SCHEMA R3 と、`detail` を記帳前に落とす
`StripViewOnly` の合わせ技。**画面には出ていて、台帳にだけ残っていない**）。

ここで責めるべき相手はいない。**Provider は誤動作していない — 唯一可能なやり方をした。**
分割プロトコルには「誰にやらせるか」を書く場所が無く、サブタスクは親の配線を継承する
（ADR-0054 Decision 1）。だから「codex で」を満たす道は道具箱しか無かった。

そして ADR-0054 は、その空席を自分で名指ししている。per-child のルーティング抽選を
却下した理由3は、こう書いてあった:

> **これは tomobit がオーケストレーションを始めるということ。** VISION の
> 「Tomo はオーケストレータではない」に正面から触れる。**分割の中身をどう配るかは、
> 分割を提案した Provider の采配であって、tomobit の仕事ではない**

読み直すと、あれが禁じたのは **tomobit が配ること**である。同じ文で
**配るのは提案した Provider の采配だ**と明言しながら、采配を表現する語彙を渡していない。
**ADR-0054 は席の名前を決めて、そこを空席のまま置いた。** 今日の抜け道は、その空席から
漏れている。

所有者の言葉を引く——「Tomo はオーケストレーターではないが、**相棒の言うことを
根拠なく拒否するものでもない**」。並走の指示が道具箱経由になるのは直感的でないし、
ハーネスという製品としても弱い。

---

## Decision 1: 判断は運ばない。しかし指示は運ぶ

線をここに引く。

- **tomobit が自然文を解釈して Provider を切り替える** → 判断の座席を作る。
  ADR-0011 違反。**採らない**
- **Provider が「ユーザーは codex にも訊きたがっている」と読み取って宣言し、
  tomobit が写す** → 意味はモデル、tomobit は運搬。既存の作法そのもの。**採る**
- 人が明示コマンドで指定する → 人の判断。筋は通るが**本ADRでは扱わない**（Consequences）

この線の上では、**指示を運ばないことのほうが VISION 違反になる**。Companionship は
命令と実行の関係ではないが、相棒の言ったことを構造的に聞き取れない harness は、
相棒ですらない。

## Decision 2: 群の要素に実行者を持たせる

分割提案のスキーマを拡張する。群の要素は、**文字列** または **実行者つきの対**:

```json
{"tomobit_split": ["A", [{"do":"B","provider":"codex"}, "C"], "D"]}
```

- **文字列は今日どおり親を継承する。既定は不変** — 宣言があるときだけ実行者が変わる
- 深さ1・提案順・群＝独立宣言・総数2〜5 は**すべて不変**（ADR-0023 / 0028）
- 受理の規律も不変: マーカーが勝つ / 形式不正は警告して通常続行 /
  自己エコー弾き（`isExampleEcho` を新しい例に対応させる）/ exit≠0 は読まない

追加する規律は2つだけ:

- **未知の Provider 名は、その子だけ親継承に落として警告する。** 提案全体は捨てない。
  1語のタイプミスで4本の作業を失うのは割に合わない
- **`human` の指名は受理しない。** ADR-0054 Decision 1 の「内訳の一部だけを人へ
  差し戻さない」を維持する。人へ渡したいならタスクごと渡す道が既にある

**tomobit は宣言の妥当性を判定しない**（ADR-0028 Decision 2 と同じ）。
「そのサブタスクは本当に codex 向きか」は意味の問題であり、Provider の領分である。

## Decision 3: プロトコル文に2行足す — 訊き方を足すだけで、解釈はしない

`subtask.Instruction` の決定的テキストに、規範を2行足す:

- ユーザーが**実行者を名指しした**ら、宣言で表せ。**自分で別の CLI を起動するな**
- ユーザーが**並列を明示した**ら、それを尊重せよ

1行目が本ADRの穴を塞ぎ、2行目が「並列で」という指示そのものの取りこぼしを塞ぐ。
どちらも tomobit は解釈しない — **訊き方を足すだけ**で、判定は Provider に残る。
プロトコル文は決定的な固定文字列のままなので、提案の不在は今までどおり
「モデルの判断」であって「訊き方のブレ」ではない（ADR-0023 Decision 1）。

## Decision 4: 指名は記帳する。抽選の標本とは分けられる形で

指名された実行者は ADR-0012 の抽選を上書きする。その結果は当然台帳に載る
（`openSubtask` は既に子ごとに `capability.started` を書いており、実行者が変われば
`provider.selected` も正しく codex になる。**台帳が真実を語るようになる**）。

そのうえで、**「指名された」ことを記帳する。**

理由は選択バイアスである。人が codex を名指しするのは「codex 向きだと思ったとき」
なので、指名された実行の成否は**抽選で選ばれた実行の成否と同じ母集団ではない**。
混ぜたまま事後分布に入れると auto の学習が歪む。ADR-0044 が「観測」と「推定」を
分けたのと同じ作法で、**後から分離できる形で残す** — いま分離規則を決め切らずとも、
分離できないデータにしてしまう事故だけは避ける。

kill switch は config に置く（`*bool`、nil = ON。`split_protocol` /
`parallel_subtasks` と同じ形）。指名を受理しなくなれば、挙動は今日に戻る。

## Consequences

- **道具箱からの剥奪は不要になる。** 検討したが取り下げた。正規の口ができれば、
  禁止は「代替なき禁止」から「規範＋代替」に変わる（Decision 3 の1行目がその規範）。
  そして**剥奪しても保証にはならない** — `curl` も MCP も Provider 自身のサブエージェントも
  塞げない。塞げるのは「たまたま目に見えた形」だけで、**塞いだつもりになるほうが危ない**
- ADR-0059 の但し書き（数えられない本数がある）は**残る**。正規化は動機を減らすが
  経路を消さない。逆に、宣言経由で走る子は tomobit が起動するので**入場をきちんと取る**
- **GUI はほぼ変更不要**。`newView(w.adapter.Name(), …)` が既に Provider 名を
  フレームに載せているので、`subtaskWiring` が子ごとになればチップにそのまま出る
  （GUI ADR-0011 の並走子フレーム。実装時に確認する）
- **ADR-0054 Decision 1 の改版範囲は「既定への降格」だけ。**「子ごとに抽選しない」
  ことは不変であり、tomobit が配らないことも不変である。変わるのは
  「親の相手で走る」が**唯一の道**から**宣言が無いときの既定**になる点だけ
- **作業ツリーの共有は要確認。** 別 Provider の子が同じツリーを触る問題は、
  ADR-0026 が duel で既に指摘したものと同型である。ADR-0050 の隔離プロトコルが
  そのまま効くかは実装時に確かめる
- 費用の概算行は、指名先が費用を報せなければ「概算なし」に落ちる。
  ADR-0028 の「作り話の金額を出さない」がそのまま効く
- プロトコル文の拡張分は固定トークン費。ADR-0028 が約束した実測に相乗りする
- 却下: **tomobit が自然文から意図を抽出する**（Decision 1）
- 却下: **duel をユーザーから呼べるようにする**。隣接するが別物である —
  duel は「どちらが良いか1つ選ぶ」比較で、今回求められたのは敵対的検証、つまり
  **両方の成果を統合すること**だった。判定の形が噛み合わない
- 保留: **chat の明示コマンド**（`/with codex` のような、Provider を介さず人が直接
  指名する口）。人の判断なので筋は通るが、まず Decision 2 で足りるかを運用で見る。
  「codexでも」と自然文で言う人が、コマンドを打ってくれるとは限らない

## 実装の記録（2026-08-08）

Decision 1〜4 は書かれたとおりに実装した。以下は**本文が決めていなかったこと**と、
Consequences が実装時に確かめると書いた項目の結果である。

**記帳先は `task.started` の `named_provider`。** Decision 4 は「指名されたことを
記帳する」とだけ言い、場所を決めていなかった。`provider.selected` はアダプタ自身が
発行するイベントで、アダプタは指名を知らない — そこへ足すのは他人の発行物の書き換えに
なる。子が生まれた時点の事実として `task.started` に1フィールド置けば、新しい type も
SCHEMA の型追加も要らない（封筒方式）。**記録するのは宣言された名であって解決結果では
ない**: 親継承に落ちた子はキーを持たず、起きなかった配線を主張しない。

**指名が通らない場合を3つに揃えた。** 未知名（Decision 2 が明記）、`human`（同）、
kill switch。どれも**その子だけ親継承＋理由を表示**で、提案全体は捨てない。
4つ目として、**親が `human` のときは指名を受理しない**を足した — 本ADRは触れて
いないが、人が担うタスクの分割に Provider の宣言は存在せず、現れたものを配線に
昇格させる理由がない。既定（親継承）に倒すほうが本ADRの姿勢に合う。

**プロトコル文の例は変えていない。** Decision 3 は「訊き方を足すだけ」なので、
埋め込みの JSON 例は文字列のみのまま置き、対の形は規範の行の中で示した。例を対に
書き換えると、**既定は文字列**という姿勢がその1行から消える（ADR-0054 D1 の既定は
不変、が本ADRの前提である）。固定トークン費も、例を増やすより行を足すほうが小さい。

**作業ツリーの共有は問題なかった**（Consequences の宿題）。ADR-0050 の隔離は
プロトコル文であって VCS の語彙を持たないので、**どの Provider にも同じように効く**。
かつ `workspace.Dir` は `~/.tomobit/worktrees/<sid>` を返し、**sid は子ごとに違う** —
別 Provider の子が同じツリーを踏む経路が最初から無い。ADR-0026 が duel で指摘した
同型の問題は、隔離が sid で切られている限りここでは再発しない。

## 実測（2026-08-08・claude-code 2.1.224 / codex-cli 0.147.0・計 $0.50）

隔離した台帳（`--db`）と一時リポジトリで、`do` と `chat --view ndjson` の両経路を
1回ずつ流した。プロンプトは「2つの独立した作業を分割提案してほしい。**(2) は codex に
実行させてほしい**」。

**Decision 3 は効いた。** claude-code は道具箱へ手を伸ばさず、対の形で宣言した:

```json
{"tomobit_split": [["hello.txt を作り hello と書く", {"do": "world.txt を作り world と書く", "provider": "codex"}]]}
```

**台帳が真実を語るようになった** — 本ADRの目的そのものである:

| 子 | `named_provider` | `provider.selected` |
|---|---|---|
| hello.txt（継承） | キー無し | claude-code |
| world.txt（指名） | `codex` | **codex** |

端末には `[1:claude-code]` と `[2:codex]` が並走で並び、両方のファイルが実際に作られた。

**view には子ごとの相手が乗る**（GUI へ届くデータ。`chat --view ndjson` の実出力）:

```json
{"name":"codex","sub":2,"sub_total":2,"type":"provider"}
{"n":1,"provider":"codex","sub":2,"sub_total":2,"type":"turn.started"}
```

**費用の非対称も予告どおり。** codex の子は `cost_usd` を持たない（ADR-0028 が記録した
既知の非対称）。概算が作り話の金額を出さない規律は、指名経由でもそのまま効く。

### GUI — 経路は追えたが、画面は見ていない

Consequences の「チップにそのまま出る」は**記述が古い**。GUI [ADR-0014](https://github.com/Rererr/tomobit-gui/blob/main/docs/decisions/ADR-0014-speech-and-work-are-separated.md) が常時チップ
（`chat-turn-provider-chip`）を廃止しており、現在の provider 名は終わったターンの
**メタ1行**に出る（走行中は GUI ADR-0008 の帯が言う）。

経路は追えた: `viewFold` が `turn.started` の `provider` を `sub` ごとの枠へ保持し、
`TurnMeta` がそれをラベルに含める。**ただし実際の画面は見ていない。**
また GUI 側のテストは子の枠が `sub` を持つことは固定しているが、**子ごとに相手が違う
場合を固定していない**（既存の例はどれも同じ provider で、本ADR以前はそれが正しかった）。

## 原則

> **判断は運ばない。しかし指示は運ぶ。**
>
> 采配が Provider のものだと決めたなら、采配を書く場所を渡さなければならない。
> 渡さないまま「やるな」と言うのは、禁止ではなく怠慢である。
