## Context

ADR-0028 が並走を入れ、ADR-0056 がその許可ゲートを撤回した。上限
`parallelWidthCap`（初期3）は残っているが、**あれは群ローカルの弁である** —
`runGroupParallel` が呼ばれるたびに新しく作られる（`cmd/tomobit/split.go:488`）。
1つのタスクが機械を占有しないための弁であって、機械を守る弁ではない。

数えると、こうなる:

- GUI は最大4窓で、窓ごとに別の `tomobit chat` 子プロセスを起動する（GUI ADR-0009）
- chat のタスクを開くターンには分割プロトコルが付く（ADR-0028 Decision 1）
- 親の実行と子の群内並走は同時に立たないので、1窓あたり最大3本
- よって **1つの GUI で 12本**の Provider CLI が同時に立ちうる
- 端末の duel はさらに2本を並走させる（`cmd/tomobit/duel.go:228`）
- **2つ目の GUI、2つ目の端末は数に入らない。機械全体の上限は事実上無い**

食い合う相手は**アカウントの窓**である。ADR-0044 が観測している 5h / 7d の窓は
アカウント単位で共有されるのに、**上限だけがプロセスローカルに置かれている。**
弁が、資源と違う側に付いている。

そして、これは新しい発見ではない。GUI ADR-0009 は既にこう書いていた:

> **並走幅（本体 ADR-0028 の群並走・初期上限3）は machine-wide で見る**。
> 4窓 × 3本 = 12プロセスが、1本ずつのゲートを通って同時に立ちうる。
> presence が機械上の生存セッションを数えられるので、並走ゲートの文言に
> 「（現在ほかの窓で N 本走行中）」を足す。**判断はしない — 数を言うだけ**

正しかった。ただし**運び手をゲートに置いた**。そのゲートを ADR-0056 が撤回したので、
この決定は宙に浮いた。数える場所が無くなったまま、数える理由だけが残っている。

先例もある。**機械全体の直列化は、境界の知覚では既にやっている** —
複数の chat が同時に境界へ達しても、ローカルモデルの実行は `facelock` の
OS ロックで1本に絞られる（`internal/facelock/facelock.go` の3人目の利用者）。
同じ原始が、Provider の起動には使われていない。

### 起草中に潰した最初の設計（記録として残す）

最初の案は「機械全体で N 枚の券」という単一の財布だった。所有者の指摘で崩れた —
**4窓すべてが高難度タスクを持つと、並走の子が券を食い尽くし、他の窓の普通の会話まで
止まる。** しかも「取れなければ逐次に落とす」という降格経路も、逐次の1本が同じ財布から
券を要るので前に進まない。**並走ぶんと通常ターンぶんを同じ財布から出していたのが誤り**
だった。Decision 1 はその修正である。

---

## Decision 1: 財布を2つに分ける — 席は拒まない、絞るのはプールだけ

Provider CLI を起動する直前に入場を取る。土台は `facelock` と同じ OS ロックの原始とし、
`~/.tomobit` の下に置く（新しい機構を発明しない — 既に3人が使っている原始の4人目になる）。
ただし**取るものを2種類に分ける**:

| | 誰が使うか | 上限 | 拒むか |
|---|---|---|---|
| **席** | 1つの作業系列につき1つ。普通の1ターンでも、群の1本目でも | 無し（数えるだけ） | **拒まない** |
| **プール** | 群の2本目以降。つまり**並走ぶん** | あり（Decision 4） | 取れなければ待つ |

これで **人が直接頼んだ1本は決して止まらず、tomobit が自分の判断で増やした本数だけが
絞られる。** 4窓すべてが3本の群を持っても、1つの窓が全幅で走り、残りは席の分だけ
順に進む — どの窓も止まらない。

`parallelWidthCap` は残す。目的が違う二つの弁だからである:

| 弁 | 守るもの | 置き場所 |
|---|---|---|
| `parallelWidthCap`（既存） | 1タスクが機械を占有しないこと | 群（プロセス内） |
| プール（本ADR） | アカウントの窓が食い潰されないこと | 機械（プロセス横断） |

**キーは Provider 名では足りない。** 同じ `claude-code` でも `claude_config_dir` が
違えば別アカウントであり、窓を食い合わない。**食い合うのはアカウントの窓であって、
コマンド名ではない。** だからキーは、ローカル設定上の認証プロファイルまで区別できる
形にする。区別材料が取れない Provider は、その Provider 名をそのままキーとして扱う
（推測で束ねない）。

`human` は席もプールも使わない。人は CLI を立てないし、API の窓も消費しない。

**duel の2本目はプールから取る。** 取れなければ待つ。duel は好奇心（ADR-0026）で
あって仕事ではないので、待たせてよい — VISION の Curiosity with Responsibility が
そのまま規則になる。仕事の並走とは扱いを変える、という非対称に根拠がある。

## Decision 2: 待ちは失敗ではない。そして経験でもない

プールが空くのを待つ。`facelock.AcquireWithin` と同じく、待ちには時間の上限を置く。

- **待ち時間を Provider の実行時間に混ぜない。** 混ぜれば「この Provider は遅い」という
  嘘を台帳に書くことになり、ADR-0012 の決定則が汚れた標本の上に建つ
- **待ちは台帳に載せない。** これは配線であって経験ではない —
  ADR-0053 が `permission.required` を「view-only、台帳に届かない」と決めたのと同じ座席
- **上限まで待って取れなければ、席の分だけ順に走る。** 群は完走する。作業は失われない。
  ADR-0028 Decision 3 の「断りは中止ではなく逐次」と同じ形だが、**今度は必ず前に進める** —
  席は拒まないので、降格した先に必ず走れる道がある（これが Decision 1 で財布を分けた理由）
- 降格したことは view に出す。黙って遅くなるのが一番わるい

## Decision 3: 数は言う。判断はしない

群のヘッダ行に、ほかで走っている本数を足す。ADR-0056 Decision 2 が作った
告知行と**同じ場所・同じ姿勢**である。

```text
これまで  -- group 2/3: 2本を並走（概算 $0.42 = 直近実測の中央値 × 2本）--
これから  -- group 2/3: 2本を並走（概算 $0.42 = 直近実測の中央値 × 2本、ほかで1本走行中）--
```

GUI ADR-0009 が予定していた文言を、消えたゲートではなく**この行が引き取る**。
本体の告知行は view ストリームに乗るので、**GUI 側の配線変更は要らない**
（実装時に確認する）。

**残量の観測（ADR-0044 / 0049）は入場制御に繋がない。** opt-in の観測を、
既定で走る実行経路の判断材料にした瞬間、ADR-0049 の「沈黙は同意ではない」が裏返る
（観測を切っている人だけが別の挙動になる）。残量が何%であっても、入場の可否は変わらない。
数えるのは**自分が今立てている本数**だけで、これは観測ではなく自分の記録である。

## Decision 4: プールは 2。kill switch は置く

プールの初期値を **2** とする。導出は「**1つの窓が誰にも邪魔されなければ全幅で
並走できる最小値**」— `parallelWidthCap`（3）のうち1本目は席で賄えるので、
残りは 2 でよい。窓が4つある機械での最悪同時本数は 4（席）＋ 2（プール）＝ **6本**。
今日の 12 から半減し、しかもどの窓も止まらない。

**「実測してから決める」は採らなかった。** ADR-0028 が測ったのはプロトコル文の
固定トークン費 — 決定的な量で、1回測れば確定する。ここで測りたいのは 429 が
出始める点で、時間帯・アカウントの前歴・ベンダー側の変更で動く**非決定的な量**である。
しかも ADR-0044 の実測どおり **429 は多義**（レート制限と、プロファイル取り違えが
同じコードで返る）。加えて、測ること自体が 5h / 7d の窓を意図的に焼く。
**この項目で「計測してから」を選ぶことは、ADR-0028 自身が戒めた
「計測してからの形をした先送り」になる。**

代わりに**降格・昇格の経路**を持つ。`quota_observe` を有効にしている所有者が
429 や残量の急減を見たら下げる、運用して一度も詰まらなければ上げる。ノブなので後から動く。

kill switch は `config.provider_admission`（`*bool`、nil = ON）。
`split_protocol` / `parallel_subtasks` と同じ形にする（このキーを知らない config を
黙って降格させない）。`quota_observe` の非対称（nil = OFF）はここでは採らない —
あれは他人の資格情報に触るから既定OFFだった。**入場制御は自分の起動を数えるだけで、
外に何も送らない。**

## Consequences

- GUI ADR-0009 の宙に浮いた決定が閉じる。運び手はゲートではなく告知行になった
- **これは絶対上限ではない。** 席は拒まないので、端末を10個開けば席は10になる。
  保証できるのは **同時本数 ≤（走っている作業系列の数）＋ プール**だけである。
  弱く見えるが、これが正しい線だと考える — 絞るべきは tomobit が増やした分であって、
  ユーザーが開いた窓を tomobit が塞ぐのは越権になる
- **数えられない本数がある。** 入場は tomobit が起動する CLI にしか掛からない。
  Provider が自分の判断で別の Provider CLI を起動した本数（実測: 2026-07-30 の
  セッションで claude-code が codex を Bash 経由で起動している）は数に入らない。
  [ADR-0060](ADR-0060-the-executor-can-be-named.md) が正規の口を与えるので**動機は
  減る**が、`curl` や MCP 経由は残るので**経路は消えない**。上限 6 は
  「tomobit が数えられる範囲の上限」であり、それ以上を主張しない
- **`presence` は流用できない。** あれは機械上の**生存セッション数**を数えるもので、
  「走行中の Provider CLI 本数」とは別の数である。GUI ADR-0009 は presence を
  想定していたが、セッションは走っていなくても生きている。数えるものを取り違えない
- 却下: **残量に連動した動的なプール**。ADR-0049 が裏返るうえ、台帳ではなく
  ベンダーの数字を決定則に混ぜることになる（ADR-0011 / 0012）
- 却下: **並走の単位を窓にする**（人が窓を開いて分ける）。ADR-0056 が
  所有者の観察を根拠に却下済み。本ADRはその決定に触らない
- 却下: **プロセス内の共有セマフォ**。GUI の窓は別プロセスなので、
  一番効いてほしい12本の場面で効かない
- 却下: **群ローカルの弁を消してプールに一本化する**。1タスクが機械を
  占有しないことと、機械が窓を食い潰さないことは、別々に守る価値がある
- 却下: **単一の財布**（起草中の最初の案）。Context の末尾に記録した

---

## 原則

> **弁は、食い合う資源と同じ側に置く。**
> **そして、人が頼んだ1本は止めない — 絞るのは、自分が増やした分だけ。**
