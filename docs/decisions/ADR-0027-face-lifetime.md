# ADR-0027: 顔窓の寿命 — 対話が生きている間だけ居る（既定）／常駐は明示オプト

- Status: **Accepted**（2026-07-17、本人決定「アクティブなセッションが0になったらfaceも消える。
  ただしデフォルトがその設定なだけで、オプションで意図的に消すまで常駐も可能に」。
  `status` 単体は約3秒の一瞥で消える挙動でよい（選択肢A）と確認）
- Date: 2026-07-17
- 関連: [ADR-0025](ADR-0025-face-autolaunch.md)（Decision 2「明示的に止めない限り常駐」の
  *常駐* の意味を本ADRが分化させる）, [ADR-0020](ADR-0020-face-window.md)（顔窓＝第二のレンダラ・
  DBは読み取りのみ）, [ADR-0021](ADR-0021-onboarding.md)（config.json / 解決順 flag > env > config）,
  [ADR-0022](ADR-0022-chat-session.md)（チャットは記帳の単位＝タスク、入力の器＝会話）

---

## Context

ADR-0025 で顔窓は「対話的な入口で自動起動し、明示的に止めない限り常駐（Esc/Q で閉じる）」に
なった。結果、一度出た窓は起動元 CLI から切り離され（detach）、手で閉じるまでデスクトップに
残り続ける。「作業を始めた瞬間に相棒が居る」は達成できたが、**作業を終えても相棒が残る** —
`do` が終わっても、`chat` を抜けても、窓だけが取り残される。

本人の要望は「アクティブなセッションが0になったら face も消える」を**既定**にしつつ、
「意図的に消すまで常駐」を**オプション**として残すこと。窓の寿命を、作業の存在に接地する。

### 「アクティブなセッション」を DB セッションで測れない理由

素直には「task.started があって task.finished/cancelled が無いセッション数」（`activeThoughts`
と同じ導出）で測りたくなるが、これは窓の寿命の代理指標として壊れている:

- **chat のターン間アイドル**: タスクは最初のターンで開き、`/new` か `/exit` まで開いたまま。
  だが「まだ何も打っていない chat」や「ターンとターンの間」は task が無い＝0 になる。
  人はキーボードの前に居るのに窓が消える
- **`status`**: セッションを一切作らない。0 のまま＝出た瞬間に消える
- **`do` 完了直後**: task.finished を書いた瞬間 0 になるが、次の `do` が続くかもしれない

窓の寿命が接地すべきは「**この機械で tomobit の対話が生きているか**」であって、
DB 上のタスクの開閉ではない。プロセスの生存で測る。

---

## Decision 1: 寿命は「生きている対話プロセス数」に接地する

顔窓は、生きている `chat` / `do` プロセスが1つ以上ある間だけ「居るべき」とみなす。
既定は**エフェメラル**（0になったら閉じる）、オプトインで**常駐**（0でも Esc/Q まで残す）。

- **presence（在席）機構**: 各対話 CLI は起動時に `~/.tomobit/sessions/<pid>.lock` を
  排他 flock で保持し、終了・クラッシュで OS が解放する。既存 `facelock` の primitive
  （unix=flock / windows=LockFileEx、fd 保持で寿命管理、`ErrHeld` で「他が保持中」判定）を
  そのまま再利用する — 新しいロック実装は作らない
- **数え方（顔窓側）**: `~/.tomobit/sessions/` を列挙し、各ファイルに `facelock.Acquire` を試す。
  `ErrHeld` なら所有者が生きている（在席1）。取得できたら所有者は死んでいる（stale）ので
  即 `Release` してファイルを削除する — クラッシュで残った幽霊在席を掃除しつつ数える
- 顔窓は DB を読み取り専用でポーリングする既存ループ（ADR-0020）の中で、同じ間隔で
  在席数も読む。**書き込みは一切増えない**（顔窓は依然レンダラであり、CLI が自分の在席を
  自分で持つ）

却下した対案:

- **DB セッション基準**（task.started EXCEPT finished/cancelled を数える）→ 上記のとおり
  chat アイドル・`status`・`do` の谷で誤って 0 になる。窓の寿命の代理として壊れている
- **CLI 終了時に face を kill**（起動元が後始末する）→ マスコットは機械に1匹で複数 CLI が
  共有する（ADR-0025）。1つの CLI が抜けても別の chat が生きていれば消してはならず、
  結局この参照カウントが要る。kill 経路は detach 済みプロセスへのシグナルという別の脆さも足す
- **launchd 等の常駐 daemon** → ADR-0025 で却下済（config.json の外に OS 専用配線が増える）。
  本 ADR はむしろ逆向き（既定で消す）なので daemon 化はさらに遠い

---

## Decision 2: 自閉は「在席0が猶予秒つづいたら」— 一瞬の谷では閉じない

エフェメラル時、顔窓は在席数が **0 のまま猶予（`residentGrace` = 3s）継続**したときだけ
`ebiten.Termination` で自分を閉じる。0 を観測した瞬間には閉じない。

猶予が吸収するもの:

- **起動直後のレース**: 窓の初回ポーリングが CLI の在席登録より先に走っても、猶予の間に
  在席が現れれば閉じない。`chat`/`do` は face を spawn する前に自分の在席を取るので通常は
  最初から1だが、猶予はこの順序保証への依存を消す安全弁
- **`do` 完了直後の谷**: task.finished 後に次の `do` が続くとき、一瞬の 0 で消えない
- **`status` 単体の一瞥**: `status` は在席を持たない（Decision 3）。他に何も走っていなければ
  在席は最初から 0 で、窓は**約3秒 Tomo が顔を出してから消える**。フラッシュ（開いて即閉じ）
  ではなく意図的な一瞥であり、ADR-0025「setup 後の最初の画面は Tomo」の思想を軽く満たす

`residentGrace` は人が決めるノブ（ADR-0020 Consequences の系譜）。ポーリング間隔 500ms に対し
3s＝連続6回の 0 観測で閉じる。

## Decision 3: 各入口の在席保持

| 入口 | 在席の保持 | 帰結 |
|---|---|---|
| `chat` | REPL の生存中ずっと（起動→終了で defer 解放） | 開いている間ずっと居る。`/exit`・Ctrl-D 後に猶予→閉じる。**ターン間アイドルでも消えない**（プロセスが生きている） |
| `do` | 実行の間だけ（起動→終了で defer 解放。split/duel の子も親 `do` の在席1つが覆う） | 走っている間居る。完了後に猶予→閉じる |
| `status` | 保持しない | 他に走っている対話が無ければ約3秒の一瞥（Decision 2）。`chat`/`do` 併走中なら既存の窓がそのまま残る |

`status` が在席を持たないのは、覗き見に在席の意味論を与えないため。持たせても持たせなくても
猶予により結果（一瞥3秒）は同じなので、単純な側を採る。`record`/`perceive`/`rebuild` は
そもそも顔窓の対象外（ADR-0025 Decision 2）なので在席とも無縁。

## Decision 4: 常駐は config で、モードは「窓を出した最初のプロセスが決める」

- **設定**: `config.json` に `face_resident`（`*bool`・省略＝`false`＝エフェメラル）。
  env `TOMOBIT_FACE_RESIDENT=0|1` がセッション上書き（flag > env > config、ADR-0021 の解決順。
  その他の値は警告して既定へ — `face_auto_launch`/`TOMOBIT_FACE` と同じ規律）。
  フラグは足さない（ADR-0025 と同じ判断）
- **CLI が解決し、`tomobit-face --resident` で子へ渡す**: 設定解決は CLI 側に集約する
  （`--db` を渡すのと同じ流儀）。顔窓は自分では config を読まず、渡された `--resident` に従う
- **モードは birth-time で決まる**: マスコットは機械に1匹。窓が既に出ていれば新しい CLI は
  spawn しない（ロック保持）ので、窓のモードは**最初に出したプロセスの解決結果**で固定される。
  通常は config で機械全体が一貫するので問題にならない。env で片方だけ上書きした稀なケースは
  「先勝ち」になる — 実行中の窓へモード変更を伝播させる仕組みは持たない（1匹の状態を後から
  差し替える複雑さに見合わない）
- `tomobit setup` に質問を1つ追加（常駐 on/off・Enter で既定＝エフェメラル）。config.json を
  書くのは setup、の一貫性（ADR-0021）を保つ
- **`face_auto_launch` と `face_resident` は直交**する: 前者は「窓を出すか」、後者は「出した窓を
  残すか」。両方 ON（既定 auto-launch × resident）＝従来 ADR-0025 の挙動（出て常駐）、
  auto-launch ON × resident OFF（新既定）＝作業中だけ居る、が既定になる

---

## Consequences

- ADR-0025 Decision 2 の「明示的に止めない限り常駐」の *常駐* が二つの軸に分化する:
  **出すか**（`face_auto_launch`）と**残すか**（`face_resident`）。ADR-0025 は「窓を出す」
  規律として生き続け、本 ADR が「出した窓の寿命」を足す。README 索引に ADR-0027 を追加し、
  ADR-0025 に相互参照を追記する
- 既定の体験が変わる: これまで手で閉じるまで残っていた窓が、作業（chat/do）を終えると
  数秒後に自分で消える。従来挙動が欲しいユーザーは `face_resident: true` か
  `TOMOBIT_FACE_RESIDENT=1`
- `~/.tomobit/sessions/` が新設される。クラッシュで残った `<pid>.lock` は顔窓が数える過程で
  掃除する（stale は取得できる＝削除）。顔窓が動いていない間の残骸は無害（次の起動時に掃除
  され、ファイル自体は空）
- 在席は「生きている対話プロセス」であって「実行中のタスク」ではない。`chat` を開いたまま
  放置すれば窓も残る — これは意図どおり（人が相棒の前に居る）。窓を消したいなら chat を抜ける
- GOOS=windows のクロスビルドが通る状態を維持する（`facelock` の再利用なので新規プラット
  フォーム分岐は増やさない方針。増やす場合も既存ビルドタグ分割の慣習に従う）
