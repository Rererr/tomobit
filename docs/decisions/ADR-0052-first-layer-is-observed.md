## Context

2026-07-26 の実台帳の観測で、**ADR-0003 が置いた三層のうち第1層と第2層が一度も
発火していない**ことが分かった:

```text
test.result     0 件
user.verdict    0 件
task.finished  38 件  ← 実質これだけが台帳を動かしている
```

書き手を追うと理由が出た。`test.result` と `user.verdict` は
[perceive.go](../../internal/perceive/perceive.go) に**読む `case` があるだけ**で、
**書く側がコードのどこにも存在しない**。

これは見落としではない。ADR-0006 Decision 3 が理由つきで先送りしている:

> Phase 1のdoが**生まないもの**（明記）:
> `test.result` — **子プロセス内のテスト実行を外から決定的に識別できない**

理由は当時も今も正しい。Provider の中で走ったテストを、ストリームの外から
「これはテストだった」と決定的に見分けることはできない。

**しかしこの理由は「tomobit 自身がテストを走らせる」経路には及ばない。**
識別が要るのは他人の実行を覗くときだけで、自分で走らせたコマンドの exit code は
識別ではなく観測である。

そして学習側は**既に完全に配線されている**。
[types.go](../../internal/core/types.go) の `Outcome.TestsPassed` と `OutcomeWeight`
は、テスト失敗を「成果物への客観判定」として採用評価より上位に置き（y=0）、
テスト通過を主観の無いときの y=0.9 として既に実装している。
**欠けているのは書き手だけで、書けば学習コードは1行も変わらない。**

とりわけ効くのが**分割サブタスク**である。子は設計上 `task.finished` が空
（ADR-0028 Decision 5: 主観は聞かない）なので `Adopted` が `""` になり、
`OutcomeWeight` の「主観が無いときだけ効く」枝がそのまま当たる —
**テストが通れば y=0.9 が乗る**。2026-07-26 の計測で無信号だった子13件は、
この1本が無かったために沈黙していた。

## Decision 1: 観測は tomobit 自身が行う — Providerに宣言させない

分割（ADR-0023/0028）・隔離（[ADR-0050](ADR-0050-workspace-isolation-protocol.md)）は
「tomobitが知らないことはProviderに宣言させる」という型を作った。**第1層には
この型を使わない。**

理由は1つで、**宣言は Beta を動かす資格がないから**である。

- ADR-0050 の隔離宣言は台帳に残るだけで、`OutcomeWeight` に触れない。嘘をつかれても
  学習は濁らない（監査が濁るだけ）
- `test.result` は **y を直接決める**。「テストは通った」の自己申告が Beta を上げる
  設計は、**Providerに自分の成績表を書かせる**ことになる
- ADR-0026 Decision 3 が「機械が preference を捏造するのは正直さの軸に反する」と
  書いた線は、対象が preference でなくとも同じ形で引ける

そして決定的なのは、**ここには観測手段があること**である。ADR-0010 Decision 2 は
「観測できないものを推測で埋めない」と決めた。その裏返しとして、
**観測できるものは観測する** — コマンドを1本走らせて exit code を見るだけで、
推測も宣言も要らない。

却下した対案:

- **Providerに宣言させる**（`{"tomobit_test": {"passed": true}}`）: 上記のとおり
  自己申告が Beta を動かす。プロトコル型の一貫性より、学習信号の独立性を取る
- **Providerの出力からテスト結果をパースする**: 「パース職人芸は積まない」
  （GUI ADR-0032 で明示された規律）。しかも ADR-0006 が先送りした
  「決定的に識別できない」に正面からぶつかる
- **exit code だけで代用する**: `provider.finished` の `exit_code` は既にあるが、
  ADR-0006 が書いたとおり **exit 0 は「成果物が良い」を意味しない**。実行が
  完走したことしか言えない

## Decision 2: テストの走らせ方は配線である — 経験ではない

ADR-0047 が「働く場所は配線であって経験ではない — 台帳には書かない」と切った線を、
そのまま伸ばす。**「このプロジェクトのテストはこう走らせる」も配線**である。

`~/.tomobit/config.json` に、**働く場所からコマンドへの対応**を持つ:

```json
{
  "test_commands": {
    "/Users/me/dev/myrepo":   "go test ./...",
    "/Users/me/dev/myblog":   "npm test"
  }
}
```

- **tomobit はテストランナーを1つも知らない**。持つのは文字列1本で、
  `go` も `npm` も `pytest` も語彙に入らない（ADR-0050 Decision 1 が
  VCS の語彙を持たなかったのと同じ姿勢）
- 引き当ては**働く場所（`WorkDir`。未設定ならプロセスの cwd）に対する最長一致**。
  リポジトリのサブディレクトリへ `/cd`（ADR-0047）しても親の設定が効く。
  コマンドは**一致した鍵のディレクトリで**走る（リポジトリのルートで走らせたい、
  という素朴な期待に一致する）
- 実行は `sh -c` に通す。GUI ADR-0007 が「パイプもリダイレクトも通す＝argv分割は
  安全を買わないのに使えるコマンドだけを減らす」と書いたのと同じ判断
- **これは構造としてopt-inである**。書かなければ1つも走らない。ADR-0049 が
  「沈黙は同意ではない」と切った線に対し、**沈黙は「何も走らない」に倒れている** —
  別途 bool の同意フラグを増やす必要はない
- **走るのは人が自分で書いたコマンドだけ**である。Providerは関与しない
  （Decision 1 の帰結 — 任意コード実行の口をモデルに渡さない）

却下した対案:

- **machine-wide に1本**（`test_command`）: 複数のリポジトリを行き来する実運用で
  即座に破綻する。所有者の台帳でも働く場所は複数あった
- **プロジェクト側にファイルを置く**（`<repo>/.tomobit/test`）: 他人のリポジトリに
  tomobit の痕跡を要求する。経験主権（ADR-0018）は使用者のマシンの話であって、
  使用者が触る他人のリポジトリを汚してよいという意味ではない
- **chat の `/test <command>`**: ADR-0047 の `/cd`・`/add-dir` と同じ形で自然だが、
  セッションごとの宣言は**毎回打つ摩擦**を生む。設定は場所に紐づくものなので
  config が正しい置き場である（将来の追加ノブとしては残す）

## Decision 3: 観測はタスク境界で1回 — 分割の子には走らせない

観測は `finishTask`（[main.go](../../cmd/tomobit/main.go)）の先頭で行う。ここは
`do`・`chat`・分割の親が共有する唯一の尾部で、**器官の位置は動かない**
（ADR-0022 Decision 1 の姿勢）。

効く先:

```text
通常の do        ✓  Feedback と併走して第1層が乗る
chat の区切り     ✓  同上
分割の親          ✓  judged=false（ADR-0023 D5）で Adopted="" のため、
                     テスト通過が y=0.9 として乗る — do の分割親に初めて信号が届く
分割の子          ✗  走らせない（下記）
duel の子         ✗  同上
```

**子に走らせない理由**: ADR-0028 Decision 2 は「群は提案順に逐次で、**後の群は
前の群の成果に依存してよい**」と決めている。したがって**途中でテストが赤いのは
正常な中間状態**であり、それを子の失敗として帰属させると台帳が嘘をつく。
`OutcomeWeight` はテスト失敗を y=0 として採用評価より上に置くので、
誤った帰属の害は大きい。

分割の子は [split.go](../../cmd/tomobit/split.go) が `finishTask` を通さず直接
記帳する構造なので、**この非対称は実装上も自然に落ちる**（子に走らせないために
特別な分岐を書く必要がない）。

**正直に書く**: したがって本ADRは、2026-07-26 の計測が見つけた「子13件が無信号」を
**完全には解消しない**。解消するのは分割の**親**の側と、通常のタスクである。
子の信号は ADR-0028 Decision 5 が保留した論点（子への主観伝播）と合流したまま残る。
ただし親に第1層が乗ることで、**分割という行為の成否が初めて客観的に測れる**ように
なり、[ADR-0051](ADR-0051-orchestration-is-judged.md) の主観側と対になる。

## Decision 4: 観測できなかったものは記帳しない

`test.result` を書くのは、**コマンドが起動して終了コードを返したときだけ**である。

```text
exit 0        → test.result {passed: true}
exit ≠ 0      → test.result {passed: false}
起動に失敗     → 記帳しない（コマンドが無い・シェルが起動できない）
タイムアウト   → 記帳しない
```

起動失敗とタイムアウトを `passed: false` にしないのは、それが**成果物についての
判定ではない**からである。テストランナーが壊れていることを Provider の失敗として
記帳したら、台帳が嘘をつく。ADR-0010 Decision 2 の「観測できないものを推測で
埋めない」がそのまま当たる。

診断（何が起きたか）は stderr の人間向け面へ出す。台帳には出さない。

`test.result` の payload:

```text
test.result {passed, exit_code, duration_ms, command}
```

`passed` 以外は監査用である（perceive は `passed` しか読まない —
[perceive.go](../../internal/perceive/perceive.go)）。`command` を残すのは、
それが無いと `passed: true` が**何について真なのか**を後から言えなくなるため。
記録されるのは人が自分の config に書いた文字列そのものである。

**`test.result` は SCHEMA.md R4 の初期カタログ14種に既に含まれている。**
新しい型は増えず、payload の注記も既存の `{passed}` を広げるだけなので、
知覚の抽出プロンプト/schema は不変 → **extractor_ver のバンプ不要・rebuild 不要**。

## Decision 5: 結果は Feedback の問いに添える — 決定権は人のまま

観測は Feedback の**前**に走らせ、結果を1行だけ人に見せてから問う:

```text
テスト: 通った (go test ./... / 12.3s)
今回、どうだった? [1=文句なし / 2=まあまあ（手を焼いた） / 3=だめだった / Enter=まだ言えない]
```

ADR-0026 Decision 3 がこの形を明示的に許している:

> 将来 outcome シグナルを**補助表示**（どちらがテストを通したか）として judge に
> 添えることはあり得るが、**決定権はユーザー**

- 表示は事実1行だけで、評価の**推奨はしない**（「だめだったのでは?」と促さない）。
  ADR-0018 の主権的判断を誘導しない
- テストが赤くても人が「文句なし」と答えることはありうる。その場合
  `OutcomeWeight` はテスト失敗を優先して y=0 にする（ADR-0003 の既存の順序・不変）。
  **人の評価が上書きされる唯一の場所**であり、これは ADR-0003 が最初から
  そう決めていたものなので本ADRは変更しない
- 非TTY（GUI・スクリプト）では、この行は既存の診断経路にそのまま流れる

## Consequences

- **ADR-0006 Decision 3 の「Phase 1のdoが生まないもの」から `test.result` が外れる**。
  日付つき Amendment を ADR-0006 へ**追記済み**（2026-07-26。`user.verdict` の方は
  依然として未実装のまま — 第2層は本ADRの範囲外）
- **学習コードは1行も変わらない**。`Outcome.TestsPassed` と `OutcomeWeight` は
  既に完成している。SCHEMA は型を増やさず、`test.result` の payload 注記だけを
  **承諾時（2026-07-26）に追記済み**。**rebuild も extractor_ver も不要**
- **第2層（`user.verdict`）は依然として空のまま**である。本ADRは第1層だけを扱う。
  第2層は ADR-0003 が「将来の verdict コマンド」と書いたまま宙に浮いている —
  別の論点として残す
- **分割の子の無信号は残る**（Decision 3）。ADR-0028 Decision 5 の保留と合流する
- **副作用のあるコマンドが毎境界で走る**。人が自分で設定した場合に限られるが、
  「テストのつもりでデプロイを書く」ことは可能である。config の説明文で
  「毎回のタスク境界で走る」ことを明示する
- **時間**: 遅いテストはタスク境界を遅くする。タイムアウトをノブに持ち、
  超過は無信号（Decision 4）
- **[ADR-0050](ADR-0050-workspace-isolation-protocol.md) との相互作用**: 隔離が
  実装されると、Provider の成果は worktree 側にあり、config の working_dir で
  テストを走らせても**成果を見ないまま緑になる**。ADR-0050 を実装する際は、
  観測先を `task.workspace` の `path` へ寄せる必要がある。**本ADRを先に入れるなら、
  ADR-0050 の実装時にこの1点を必ず拾う**
- **索引**: `README.md` のADR索引へ追加済み（2026-07-26 承諾時）

## 実測（2026-07-26 実装同日・使い捨て台帳での通し確認）

環境: 使い捨ての `HOME` と `TOMOBIT_DB`（実台帳は無汚染）、`--provider human`
（LLMを呼ばないので実費ゼロ）。主観Feedbackは**一度も与えていない**（EOF = 無信号）。

観測コマンドを `test -f <path>/ok` に設定し、ファイルの有無で通過/失敗を作った。

```text
1回目（ファイルあり）
  テスト: 通った (test -f …/ok / 0.0s)
  今回、どうだった? [1=文句なし / …]        ← 事実が問いの直前に出る（Decision 5）

2回目（ファイルなし）
  テスト: 落ちた (test -f …/ok / 0.0s)
```

台帳:

```text
events        test.result {passed:true,  exit_code:0, duration_ms:5, command:"…"}
              test.result {passed:false, exit_code:1, …}
experiences   outcome.tests_passed = 1 / 0        ← 知覚が経験まで運んだ
connections   capability | cap=implement | human | α=1.9 | β=2.1
```

**Beta が第1層だけで動いた。** 事前 Beta(1,1) から、通過が y=0.9 で α を +0.9、
失敗が y=0 で β を +1.0 へ運んでいる（`OutcomeWeight` の既存の枝がそのまま効いた —
学習コードは1行も変えていない）。

**これは今まで一度も起きたことがない。** 2026-07-26 の実台帳の観測で
`test.result` が0件だったとおり、第1層は書き手が無いために構造的に沈黙していた。

確認できたこと / まだ確認していないこと:

- ✅ 通過・失敗の両方が記帳され、知覚を通って Connection まで届く
- ✅ 主観が無い（`Adopted=""`）状態で y=0.9 が乗る — **分割の子と同じ条件**なので、
  子に走らせる判断をした場合に信号が乗ることの裏取りにもなっている
- ✅ 配線されていない場所では1バイトも書かず、1行も言わない（ユニットテスト）
- ✅ 起動できないコマンド・タイムアウトは記帳しない（ユニットテスト）
- ⚠️ **実 Provider（claude-code / codex）での境界は未確認**。`--provider human` は
  finishTask の同じ尾部を通るので配線としては同一だが、実タスクの所要時間下での
  テスト実行（遅い suite・タイムアウト）はまだ測っていない
- ⚠️ **chat 経路の `/cd` との組み合わせは未確認**（`do` の cwd 経路のみ実機で通した）

## 実装フェーズ（Proposed）

1. **config と観測器**: `test_commands` の読み込みと最長一致、`sh -c` 実行、
   タイムアウト、`test.result` の記帳。純関数（一致・payload組み立て）は

   実タスクの境界で `test.result` が記帳されることを確認する

## 追記（2026-07-27）: 第1層を生やしたことが、第2層を必要にした

本ADRの Consequences は「第2層（`user.verdict`）は依然として空のまま」と書いて
論点を残した。翌日 [ADR-0055](ADR-0055-verdict-is-a-veto.md) がそこに書き手を
足している。**本ADRが原因である。**

`OutcomeWeight` の導出で、観測が回答より上に立つ場所は1つしかない:

```text
Reverted (3=だめだった)    → 0       人
TestsPassed=false        → 0       機械  ★
Adopted as-is (1=文句なし) → 1.0     人
```

★は本ADRが作った席である。`test.result` が0件だった間、この行は一度も発火せず、
第2層が空でも誰も困らなかった。書き手が入った瞬間、**テストコマンドが的外れ
だった日・テスト自体が壊れていた日、`1=文句なし` が黙って y=0 に潰される**という
実害が生まれた。

ADR-0055 はそこに1問だけ置く: **赤テスト × 1=文句なし**のときだけ、
「テストは赤だったけど、文句なし?」と訊く（既定N）。

本ADRの Decision は1つも変わらない。特に:

- **Decision 1「Providerには宣言させない」は不変。** 拒否権を持つのは人であって
  Provider ではない。「自分の成績表を書かせない」線はそのまま
- **Decision 4「起動失敗・タイムアウトは記帳しない」も不変。** 記帳しなければ
  ★が発火しないので、矛盾の問いも立たない — 壊れたテスト環境への正しい応答は
  「無い観測」であって「人に拒否権を使わせること」ではない
- **観測は消えない。** y と答えても `test.result` は赤のまま台帳に残り、経験の行の
  中で `tests_passed:false` と `verdict:"up"` が共存する。テストは実際に赤かった
  という事実は真実であり、それをどう裁くかが判定である
